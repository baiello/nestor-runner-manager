# Security of the runner service

How the local service (`core/`) meets the service criteria of contract v2 (KCA-724, S8 and S9), with the amendments of the security review (KCA-727, A1 to A7), Brice's decisions B1 and B6 (KCA-716), the single launch contract with `run-once` (KCA-734) and the fixes of the second security review (KCA-733: É1, É2, M1, M3, F1, F3, F4). What is real, what is simulated and what is still missing is listed at the end.

## Principles

1. **The local control is never a security boundary** (principle 7). Pause, ceiling, scope rule and anti-duplicate launches are good-faith regulation. Exclusive execution, the lease ceiling, the pause and the scope rule are enforced by Nestor at claim time (S6).
2. **"Never interrupt" applies to pause and to lowering the ceiling only** (principle 8). Revocation, disassociation and a forced stop from the diagnostics end running tasks.

### Launch contract v1 with `nestor-runner run-once` (É1, KCA-734)

The service and the runner speak one contract, written in nestor (`docs/run-once-contract.md`) with fixtures that this repository vendors in `contract/run-once-v1.json`. `tests/contract_fixtures.rs` checks the launcher and the report reader against them; `examples/run_once_double.rs`, the double used by `tests/process.rs`, refuses any launch that breaks them.

- **`argv`** (no shell, no secret): `run-once --runner-id <hex> --generation <n> --machine-id <uuid> --server https://<instance> --credential-fd 3 --report-fd 4`. The machine id must be a lowercase UUID and the instance a plain host name, or nothing is launched. **Never `--scope`** (É2).
- **fd 3**: the credential, as one JSON object `{"runner_token":"…"}` (16 KiB at most), written then closed by the service, only once the runner's pid is saved (KCA-741). The service holds no Claude Code token, so the optional `claude_code_token` field is left out (A7): the Mac's user keeps one once with `nestor-runner claude-token set`, in their login keychain, which the runner reads.
- **fd 0**: drain only. The service writes `drain\n`, then closes it; the end of input is a drain too, so a dead service never leaves a runner claiming.
- **fd 4**: reports, read as **untrusted** input (a process the runner started could forge them): one JSON object per line, 4 KiB at most, 20 a second, `"v":1`, a known `type` with exactly its fields (`hello`, `claimed`, `finished`, `idle`), `hello` first and once, one `claimed` per process; the rest is ignored and counted in the runner's log. A `hello` whose contract, runner id, generation or pid differ from the launch terminates the runner. A claim report carries an opaque job id and nothing of the job's content. A forged report can at worst hold a slot until the process exits; the exit always frees it.
- **Exit codes** decide how the runner ended: 0 normal; 64 usage (`failed`, never relaunched); 65 unreadable credential and 70 internal error (crashes, backoff); 75 Nestor unreachable (backoff, not counted as a crash); 77 credential refused (`failed`, no relaunch, and no runner at all is launched until the connection changes); a signal is a crash unless the service sent it.
- Every other descriptor of the service is close-on-exec: the runner inherits 0 to 4 only (checked by the double).
- The runner's standard output and error are read with a bound per line (8 KiB kept, the rest of the line dropped), so a process that writes without newlines cannot exhaust the service's memory (KCA-732 nº4).

### Credential handling (B5, A3)

The service never stores a runner credential. For each launch it asks Nestor for a fresh one (`POST /machine/runners/{id}/token` for the runner of the machine on Nestor this local runner stands for, created once with `POST /machine/runners` `{}`; proof of possession of the machine key, one claim per token per A3, scopes computed by the server; the map of local to Nestor runner ids is kept with the secrets, no token in it) and writes it, as the JSON object above, to a pipe the runner inherits as fd 3, reads once and closes. It is never in an argument, the environment or a file. The runner's environment is cleared, then given `PATH`, `LANG` and its own `HOME` and `TMPDIR`. Checked on real processes in `tests/process.rs`.

### Recoverable launch: no credential before the pid is saved (KCA-741, KCA-732 nº2)

A runner can claim nothing before it has read its credential on fd 3, so the service uses that as a barrier: a process it might lose track of in a crash never holds a job. A launch goes in four steps, under the supervisor's lock:

1. the **launch intent** is saved durably: the runner record gets `launchingSince` (now, on the clock the kernel records process start times with) and its new generation. If this save fails, nothing is spawned;
2. the process is spawned; it blocks reading fd 3;
3. its pid and start time are saved durably, and the intent cleared, in the same atomic write;
4. **only then** the credential is written to fd 3 and the pipe closed, and the service starts following the process (output, reports, exit).

If step 3 cannot be saved, the process is killed with its group and collected before it got anything (the pipe closes unwritten), and the launch counts as a crash (backoff, `failed` after 5 in a row). A pending launch that is dropped without being released is killed the same way.

After a restart, `reconcile` handles every record that still has an intent **before anything is launched**: it looks for live processes of the same user whose `argv` carries the record's `--runner-id` and `--generation` and that started at or after `launchingSince`, kills each (identity checked just before, then its group), waits up to 2 s for them to be gone, and clears the intent. A generation is never reused for a spawned process (it is saved with the intent before the spawn), so these can only be that launch's. If one cannot be ended, the intent is kept, the runner is left `failed` and cannot be started or removed until a later start of the service clears it, so no replacement ever runs beside it. In practice the orphan usually exits by itself (exit 65): the service that held the other end of fd 3 is gone. The barrier does not rely on that.

Limits: the "started after the intent" check uses the wall clock on macOS, so a backward clock step of the order of the few milliseconds between steps 1 and 2 could hide the orphan from `reconcile`; it would still never get a credential, and would end on its own when its fd 3 reaches end of file. Tested on real processes in `tests/process.rs`: the credential is not received while the pid is being saved (asserted by the store, with a double that marks the first byte on fd 3); a save failure at step 3 kills the process, which never gets its credential; a service frozen between spawn and save leaves a live process that the next service's `reconcile` ends, after which exactly one process of a new generation runs. `tests/persistence.rs` covers the same rules on fake runners (no spawn without a saved intent; an intent left behind ends its process before any launch).

### M3: what an ended runner leaves behind

The runner puts Claude Code in a process group of its own, so a `SIGKILL` to the runner's group does not reach it, and its orphans go to `launchd`. The service therefore sweeps (`core/src/sweep.rs`):

1. at the end of the grace period, **before** the `SIGKILL`: a snapshot of the runner's descendants (by parent, recursively) and of every process of the same user whose current directory or an open file is under the runner's directory (or whose `HOME`/`TMPDIR` is, where the system shows another process's environment: recent macOS versions do not), with pid, start time and process group;
2. **after** it: each process of the snapshot is killed, then the group it leads, only if pid and start time still match (never a reused pid, never the service's own group); plus whatever is found under the runner's directory again. Up to 3 passes, 1 s apart. What survives leaves the runner `failed` and raises a machine error, never a silent success.

The same sweep runs after **every** exit of a runner, whatever its status (KCA-760): the real `run-once` handles `SIGTERM` and exits 143, a normal status, and a runner that exits 0 can leave a process behind too. Then the snapshot is what is still in the runner's group when it ends (noted before the process is collected, so the group's id names no other process), plus a snapshot taken before a kill, if any; then whatever is under its directory. It runs **before** the supervisor hears of the exit, so the runner's slot is not freed and its directory not erased while something it started runs. Adopted runners (not the service's children) are swept when their end is noticed, and runners found ended at the start of the service before anything is launched. What survives leaves the runner `failed` **and keeps its slot**: it still counts against the ceiling, pinned to its scope, so no runner of another workspace starts beside it; it is started or removed again only once a new sweep finds nothing left. **Residual risk, accepted for this slice:** a descendant that leaves the group *and* moves its current directory out of the runner's directory without keeping a file open in it escapes. The real barrier is a sandbox or a dedicated user account (to list among the things to prepare). Tested in `tests/process.rs` (a runner deaf to SIGTERM with a grandchild in another group and an orphan after `setsid`: both gone within 5 s; the residual case survives, as documented; a runner that handles `SIGTERM` by exiting 143, and one that exits 0, each with a child in a new session left in its directory: the child is gone before the slot is freed), `tests/supervisor.rs` and `tests/persistence.rs` (survivors keep the slot, including for adopted runners and runners found ended at start), and `sweep` unit tests (a reused pid is not signalled).

## B1(b): no tasks of different workspaces side by side

Brice's decision: concurrency above 1 is limited, for now, to tasks of the same scope (workspace). This is **not** an acceptance of the risk of running several workspaces under one macOS user (A1): what actually protects one task from another today is the confinement of the tools (Claude Code restricted, no shell, per-job `HOME` and `TMPDIR`), not the number of tasks. Any tool that runs commands requires B1(a), dedicated runner accounts.

**What the service does (regulation).** The service **never passes `--scope`** and **applies a ceiling of 1** until Nestor announces `capabilities.scope_filter` (S6): the ceiling the user asked for is kept and shown, with "limited by the server" (`effectiveMaxConcurrentTasks`, `cappedByServer`). Passing a scope filter to an API that ignores it is what exposed another workspace's job (É2): without a filter, the runner claims what the administrator assigned to the machine, which is the intended behaviour. The guarantee that a job of another scope is never handed out can only come from the server: the scope filter belongs in the atomic claim, and a claim that matches nothing returns no job content (S6). Once S6 is announced, the local regulation below applies on top: while more than one runner may be alive, every live runner is pinned to the same scope; a runner whose scope is unknown blocks further launches until it ends; a runner that reports a job outside its scope raises `scope.violation` (contract v1 reports no scope; it comes back with S6).

**What the server must do (enforcement, S6 and A2).** The local rule cannot guarantee the property: Nestor picks the job at claim time, and the eligible count per scope is only a snapshot. Nestor must therefore **apply the scope at claim time**: honour the restrictive scope filter the runner sends, and refuse a claim of another scope while the machine holds an active lease in a different one. This belongs to S6 (lease with fencing, ceiling and pause on the server), with its concurrency test, and must be in place before any real use with more than one task at a time.

## S9: association

- **Key first.** `associate` generates the machine key before contacting Nestor and sends only its public part. Live: a P-256 key generated in the **Secure Enclave** (non-exportable), kept in the data protection Keychain.
- **Device authorization** (RFC 8628). The connection becomes `associating` with a user code and the address of the Nestor page; an **administrator** approves it there (B6). The device code is secret: in memory only, masked everywhere, never stored. Polls follow the server's interval and are signed with the machine key. Denied or expired: the key is erased. Cancel is possible.
- **Credential storage.** The machine credential goes to the **data protection Keychain**, whose access is bound to the code signature (team and access group), not to a path (N2).
- **M1, the owner confirms the account.** Nestor's last poll gives the credential with `account_email` and `approved_by_email`, masked by Nestor. The connection becomes `confirming`: the interface shows both, and **no runner is created, no heartbeat or queue is sent** until the owner confirms them on the machine (`confirmAssociation`). Refused, the machine disassociates itself and erases its secrets. Kept across a restart of the service. The interface tells the owner never to give the user code to anyone, nor type one someone gave.
- **States** `associating`, `confirming` and `revoked` are exposed to the interface.
- Tested against a fake Nestor (`nestor::FakeNestor`), which answers the machine routes of nestor #156 and #157 from the request as it goes on the wire and applies the server rules the service relies on: hashed single-use device code, expiry, approval on the web only, the proof below, leases, revocation. `tests/association.rs`.

### M2: the proof `nestor-machine-proof/v2`

Every request of the machine carries `Nestor-Machine-Proof: <ms>.<base64url DER signature>` by the machine key of seven lines (`nestor::proof_message`, nestor `docs/machine-proof.md`): the format, the **audience** (`https://<instance>`, the API the service was configured with, never one read from an answer), the real **method**, the **path and query**, the time, the base64url SHA-256 of the **secret** the request authenticates with (the machine credential, or the device code for a poll or a cancellation, empty for the request of association) and of the **body**.

Nestor accepts a proof only signed **strictly after** the last it accepted for the machine (or for the request of association), within 60 s of its clock. `MachineClient` therefore signs and sends every request under one lock, at `max(now, last + 1)` ms: the queue and a runner token issued in the same millisecond never collide. A `401 stale_machine_proof` is signed again with a new time and sent again (3 times at most); refused still, the service reports that the machine's clock is off. Tested in `tests/association.rs` (same millisecond, retries, another instance's audience refused) and against the real runner in `tests/contract_run_once.rs`, whose fake refuses a proof replayed, earlier, out of the window, or bound to another audience, method, target, query, credential, body or key.

### Heartbeat, queue and leases (nestor #157)

Associated and confirmed, the service sends `POST /machine/heartbeat` at the interval the server gives (15 s): protocol 1, service mode, mode, the ceiling it applies, its configuration revision and coarse measures (CPU and memory rounded, memory pressure, free disk); no path, name or argument. It then reads `POST /machine/queue` with what its runners offer (the tools and kinds `run-once` claims), and launches for the eligible jobs of a scope **minus the runners already waiting for one**. Both answers carry the leases and capabilities: the ceiling applied is 1 until `capabilities.scope_filter`, then the requested value within `leases.administrator_max`; `paused_by_administrator` blocks new launches (`pausedOnNestor`) and interrupts nothing. The service still passes **no `--scope`** (KCA-734 §3): the server keeps one scope at a time on a machine (A2), the local pinning of runners to one scope is good faith on top, and a runner given `--scope` gives a job of another scope back with `release` (`capabilities.release`). Tested in `tests/association.rs` (heartbeat body and rate, administrator limit and pause, no scope filter → 1, several tasks of one scope never mixed with another).

### A6: signing prerequisite and the software fallback

The Secure Enclave key and the Keychain access group need a **signed build** with a `keychain-access-groups` entitlement, so an Apple Developer certificate (a purchase, to be validated by Brice). An unsigned build gets an error (`errSecMissingEntitlement`, `-34018`, or `-25308` here) and the service reports it: **association is impossible until the signing is in place**. The weaker fallback of A6 — a software key kept in the Keychain — is coded behind the `MachineKeyStore` interface (`SoftwareKeyStore`, `KeyStoreWithFallback`) and **disabled**: the service binary never enables it, and enabling it is Brice's decision. Tested both ways in `secrets` unit tests and `tests/association.rs`.

**Decision of 2026-11-01:** no certificate and no notarization for now; the trials are signed ad hoc. With the start before login (below), the Keychain is out of reach too until the account logs in: the trials need the software key and the credential out of the Keychain, in files of the data directory, readable by the account that runs the tasks. That is Open 1 of [launch-daemon.md](launch-daemon.md), with its risk and recommendation; it stays off until Brice accepts it and a security review of the file store.

## Preparing a real installation (contract §6.B), with the N3 correction

Nothing of this is authorized or done in this lot.

**Decision of 2026-11-01:** start before login, as a LaunchDaemon installed by Brice with `sudo`, running as Brice's own account, without a second account. Its contract is [launch-daemon.md](launch-daemon.md): the binaries and the plist are owned by root and not writable by the account (D3), which meets §6.B.2 with one account, where the LaunchAgent could not.

- **§6.B.2 (unchanged):** the binary and the plist must not be modifiable by the account that runs the tasks. With a LaunchAgent under the user's own id, a task that escapes its confinement can modify them: acceptable only with B1(a) or an explicit acceptance.
- **§6.B.3 (corrected, N3):** the LaunchAgent stays the first recommendation **only with B1(a)** (dedicated runner accounts, which cannot write the service's binary and plist) **or with Brice's explicit acceptance of that risk**. B1(b) does **not** make it acceptable: limiting concurrency to one scope protects neither the binary nor the plist. If B1(a) is chosen, a LaunchDaemon or a LaunchAgent of an account dedicated to the service is to be compared.
- **§6.B.5:** signing and notarization are a prerequisite (A6, above), not a convenience.

Observed while testing: when many runner processes are launched at once by the test suite, a freshly executed stand-in runner was occasionally killed (SIGKILL) before its first report.
